# 网络对战可行性评估（阶段 8 立项前置调查）

> 2026-08-30 · 结论先行：**可行，推荐「锁定步进 + 输入延迟」简单方案（预估 2-4 次迭代）**；
> 回滚网络（rollback）体验更优但需状态快照/恢复能力，成本翻倍，暂不建议。

## 一、现有架构对联网的友好度（逐项核对）

| 条件 | 现状 | 结论 |
|---|---|---|
| 固定步长模拟 | 60FPS 固定步长 `Fight.step()`，无帧率耦合逻辑 | ✅ 具备 |
| 输入即完整驱动 | `mech.input` 字典是唯一输入面，AI 与真人同构 | ✅ 具备（只需传 9 个 bit/帧/侧） |
| 模拟确定性 | [31] 已证明：同一输入序列回放，hp/坐标/比分**逐点一致**（1356 帧零偏差） | ✅ 已被测试固化 |
| 全局随机源 | `effects.RNG` 仅用于粒子/伤害数字偏移/震屏——**纯装饰**，不影响判定 | ✅ 可容忍（各端画面粒子略异，判定一致） |
| 帧内时序 | `_combat` 结算顺序已对称化（5A 修复），无"先手窗口" | ✅ 具备 |

**核心论据：[31] 对局录像回放 = 单机版 lockstep 演练。** 录像回放能逐帧一致，意味着
"两端跑同一模拟、只同步输入"的架构在本地已被验证。

## 二、推荐方案：锁定步进 + 输入延迟（lockstep + input delay）

- 每帧每侧上行 9 bit 输入（9 个动作键），打包 ~2 字节/帧，60Hz ≈ 120 B/s/侧，带宽可忽略。
- 本地输入延迟 3 帧（~50ms）：第 N 帧模拟使用第 N-3 帧宣告的输入，未到达则重发（可靠
  UDP 或 TCP 均可，TCP 在此包频下通常够用）。
- 断线处理：超时即判负（格斗游戏惯例），无需状态恢复。
- 需要新增：`NetSession`（收发/缓冲/重发）、`InputSource` 抽象（本地键盘/手柄 → 会话），
  `Fight` 不改——回放注入通道（`scripted`）可复用为"远端输入注入器"。

## 三、为什么不推荐回滚网络（rollback）

- 需要「保存帧首完整状态 + 快进 N 帧重模拟」：Fight 状态分散在两个 Mech（20+ 字段/个）、
  fx（弹幕/粒子）、replay 队列——需要实现序列化快照并保证恢复后逐字节一致。
- 回滚的价值是消除 3 帧输入延迟的操作延迟；本项目节奏偏街机、玩家预期适中，3 帧
  延迟（50ms）在局域网/同洲可接受。
- 若未来要做：先给 Fight 实现 `snapshot()/restore()`（也是 Training 状态复制、AI 自博弈
  批量模拟的基础设施），再上 GGPO 式回滚。
